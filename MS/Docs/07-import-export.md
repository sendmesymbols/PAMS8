# 07 - Import, Export and Persistence

How a host saves and loads PAMS8 work: plan files, symbol JSON, GeoJSON, and
PowerPoint (.pptx) export and import.

Related documents: [README](README.md) | [02 Symbol Engine API](02-symbol-engine-api.md) | [08 Settings](08-settings.md) | [12 Briefing, Collab, Stylus](12-briefing-collab-stylus.md) | [14 FAQ](14-faq-troubleshooting.md)

Source: `MS/Engines/ImportExport/*` (`SerializationEngine.ts`, `Plan.ts`, `PptxExporter.ts`, `PptxImporter.ts`, `PptxComments.ts`) and `MS/Engines/PptxExportCommands.ts`.
`MS/Engines/ImportExport/IOEngine.ts` exists but is an empty file; it exports nothing.

## 1. Formats at a glance

| Format | Produced by | Read by | Contents | Version marker |
| --- | --- | --- | --- | --- |
| Plan (`poObj` JSON) | `savePlanToFile()` | `loadPlanFromFile()`, `loadPlanSymbolsFromData()` | Symbols grouped in overlays, legacy `drawEss` schema | None in the document (see section 8) |
| PAMS8 symbol array (JSON) | `saveToFile()`, `exportLayerToJSON()` | `loadFromFile()`, `importLayerFromJSON()` | Flat array of `pams8-symbol` objects | `pams8Version: '2.0'` on each item |
| GeoJSON `FeatureCollection` | `saveToGeoJSONFile()`, `exportToGeoJSON()` | `loadFromFile()` / `loadFromGeoJSONFile()`, `importFromGeoJSON()` | One feature per graphic, PAMS8 payload in `properties` | `properties.pams8: true` |
| Briefing document (JSON) | `BriefingEngine.exportBriefing()` | `BriefingEngine.importBriefing()` | Slides only, not map graphics; see [12](12-briefing-collab-stylus.md) | `version` 1 to 12 |
| PowerPoint `.pptx` | `exportPptxDeck()` | `BriefingEngine.importPptxFromFile()` | Briefing slides as a deck | n/a |

A plan or symbol file holds map graphics. A briefing document holds slides that refer to graphics by `graphic.attributes.id`. To restore a briefing fully, load the plan and the briefing.

## 2. Reaching the API

`SerializationEngine` is a singleton that `SymbolEngine` starts during construction, wiring its "load one symbol" callback to `SymbolEngine.loadSymbolFromJSON` and its template callback to the template loader. It is exposed as `symbolEngine.serializationEngine`. Most calls are also mirrored on `SymbolEngine` itself.

| Task | `SerializationEngine` (`symbolEngine.serializationEngine.*`) | `SymbolEngine` mirror |
| --- | --- | --- |
| Download plan | `savePlanToFile(filename?)` | `savePlanToFile(filename?)` |
| Pick and load plan | `loadPlanFromFile()` | `loadPlanFromFile()` |
| Load plan object (with transform) | `loadPlanSymbolsFromData(planDoc, coordTransform?)` | none |
| Symbols to array | `exportLayerToJSON()` | `exportLayerToJSON()` |
| Array to symbols | `importLayerFromJSON(data)` | `importLayerFromJSON(data)` |
| Download symbol array | `saveToFile(filename?)` | `saveToFile(filename?)` |
| Pick and load any supported file | `loadFromFile()` | `loadFromFile()` |
| One graphic to JSON | `saveSymbolToJSON(graphic)` | none (the `SymbolEngine` copy is commented out in source) |
| One JSON object to graphic | via callback | `loadSymbolFromJSON(data): Graphic \| null` |
| GeoJSON out | `exportToGeoJSON()`, `saveToGeoJSONFile(filename?)` | same names |
| GeoJSON in | `importFromGeoJSON(geojson)`, `loadFromGeoJSONFile()` | same names |

Everything is browser-only: downloads use a `Blob` plus a temporary `<a download>`, and file loading uses a temporary `<input type="file">`. There is no built-in server or storage back end. A host that wants to save elsewhere (a database, an API) should use the pure data calls: `exportLayerToJSON()`, `exportToGeoJSON()`, `importLayerFromJSON()`, `importFromGeoJSON()`, `loadPlanSymbolsFromData()`, and `exportPptxDeck({ output: ... })`.

`SerializationEngine.getInstance()` is public, and `start(layerManager, onLoadSymbol, onLoadTemplate?)` is public, but `SymbolEngine` already calls `start`. A host does not normally call it.

### Log output

Every method reports through `EngineLogger` (Engine Log panel) rather than throwing. Failure cases (engine not started, invalid document, unparseable file) log an error and return early. Calls that return a value use a sentinel (`-1`, `[]`, `{ type: 'FeatureCollection', features: [] }`).

## 3. Plan files

### savePlanToFile(filename?: string): void

Downloads every graphic on the symbol layers as a Plan JSON file.

| Name | Type | Default | Meaning |
| --- | --- | --- | --- |
| filename | `string` | `pams8_plan_<Date.now()>.json` | Download file name |

Behavior:

- Layers are scanned in this order: `TACT`, `TACT_PT`, `FORCE`, then the legacy `milSymbols` layer. Each non-empty layer becomes one overlay. The annotation layer, sketch layer and declutter layers are not saved. Labels are regenerated by the symbol classes on load.
- The overlay name (`nameTxt`, `typeTxt`) is the layer title, or the layer id when there is no title.
- Symbol id is `graphic.attributes.id`, or a generated UUID v4 if the graphic has none.
- Graphics without `attributes.drawEssentials` are skipped. A graphic that throws during serialization is logged and skipped; the save continues.
- Coordinates are converted from Web Mercator (wkid 102100 or 3857) to WGS84 degrees and tagged `sp: "WGS1SP"`.
- Screen-pinned graphics (see `ScreenAnchorEngine` in [12](12-briefing-collab-stylus.md)) get `PINNED: true`, `PIN_X_PCT`, `PIN_Y_PCT` added to their `drawEss`.
- The header fields are fixed defaults (see section 3.2). The method takes no author, title or serial parameters.
- Each `drawEss` is passed through `Plan.normalizeDrawEssForLegacyExport()` (see section 3.3).

```ts
// Host toolbar button
saveBtn.onclick = () => symbolEngine.savePlanToFile('opord-12.json');
```

### loadPlanFromFile(): void

Opens a file picker (`.json`, `application/json`), parses the file, and restores every symbol.

Behavior:

- The file must satisfy `Plan.isPlanDocument`: a `poObj` object with a `plnOrdrOverlay` array. Otherwise an error is logged and nothing is loaded.
- Symbols with `isDelete === 'Y'` are skipped. Overlay membership is not restored: each symbol is routed to its layer by its geometry type, exactly as when drawn.
- Each `drawEss` goes through `Plan.normalizeDrawEssForRuntime()`, then `sp: "WGS1SP"` points are patched to `spatialReference: { wkid: 4326 }`, then the symbol is created through `SymbolEngine.loadSymbolFromJSON`. The symbol keeps its saved id.
- The call is asynchronous (file dialog plus `FileReader`) and returns nothing. There is no completion callback; watch the Engine Log or `document` draw events (see [03](03-drawing-and-events.md)).
- Known gap, from reading the source: this path passes only `id`, `sidc`, `amplifier` and `drawEssentials` to the loader, and the loader restores Pin-to-Screen only from top-level `pinned`/`xPct`/`yPct`. So the `PINNED` values in `drawEss` are not re-applied by `loadPlanFromFile()`. `loadPlanSymbolsFromData()` does re-apply them. Verify against your build before relying on pins surviving a plan file round trip.

### loadPlanSymbolsFromData(planDoc: any, coordTransform?): number

Loads symbols from an already-parsed plan object without a file picker. Used by the Deployment Builder to place a saved formation at a chosen anchor.

| Name | Type | Default | Meaning |
| --- | --- | --- | --- |
| planDoc | `any` (must satisfy `Plan.isPlanDocument`) | required | Parsed plan JSON |
| coordTransform | `(pt: { x: number; y: number }) => { x: number; y: number }` | none | Called for every WGS84 point (`GEOM`, `CTRL_PTS`, `BASE_LN_PTS`, `OPTIONS.GEOM`); return the moved point |

Returns the number of symbols loaded, or `-1` if the engine is not started or the document is invalid.

Differences from `loadPlanFromFile()`:

- Each symbol gets a new id `<sourceSymbolId>-<placementUuid>`, so the same plan can be placed repeatedly without id collisions. `sourceSymbolId` is passed along as well.
- `suppressDrawingLifecycle: true` is set. In `SymbolEngine` this skips the post-draw housekeeping that normally follows `onDrawEnd` (clearing measurement overlays, deactivating the proximity indicator and the rest of that handler), so a bulk placement does not disturb an active tool. The `onDrawEnd` event itself is still dispatched (see [03](03-drawing-and-events.md)).
- Pinned symbols are restored (`pinned`, `xPct`, `yPct`).
- The transform only applies to points tagged `sp: "WGS1SP"` (all points written by `savePlanToFile()`).

```ts
// Shift a saved formation 0.01 degrees east
const n = symbolEngine.serializationEngine.loadPlanSymbolsFromData(planJson, (p) => ({
  x: p.x + 0.01,
  y: p.y,
}));
if (n < 0) console.warn('Not a plan document');
```

### 3.1 Plan document schema

Types are exported from `Plan.ts` (`PlanDocument`, `PlanObject`, `PlanOverlay`, `PlanSymbol`, `PlanPoint`, and others). This schema follows the legacy PAMS plan format; names such as `plnOrdr` are legacy, not typos.

```jsonc
{
  "poObj": {
    "plnOrdrId": 1780000000000,          // Date.now() at save; also plnId
    "catCode": "PLAN",
    "creatorId": 10900,
    "updateSeqnr": 1,
    "plns": [ { "plnId": 1780000000000, "catCode": "OPLAN", "subCatCode": "Def",
                "creatorId": 10900, "updateSeqnr": 1,
                "plnStats": [ { "id": { "plnId": 1780000000000, "plnStatIx": 1 },
                                "dvlpmStatCode": "NCOMPL", "stateCode": "DRAFT",
                                "dttm": "yyyyMMddHHmmss000 ", "creatorId": 10900, "updateSeqnr": 1 } ] } ],
    "ordrs": [],
    "plnOrdrHdrCntnts": [ { "id": { "plnOrdrId": 1780000000000, "plnOrdrHdrCntntIx": 1 },
                            "nameTxt": "Sample Name", "nicknameTxt": "Plan", "serialNoTxt": "11-00",
                            "sponsorTypeTxt": "SPO", "timeZoneCode": "Z", "dttm": "...",
                            "creatorId": 10900, "updateSeqnr": 1, "placeOfIssueTxt": "Office" } ],
    "orgPoas": [],
    "plnOrdrOverlay": [
      {
        "plnOrdrOverlayPK": { "plnOrdrId": 1780000000000, "plnOrdrOverlayId": "<uuid>" },
        "nameTxt": "TacticalSymbolsLayer", "typeTxt": "TacticalSymbolsLayer",
        "seqOrdr": 1, "hierarchyType": "Simple Overlay",
        "isDelete": "N", "isShared": "N", "creatorId": 10900, "updateSeqnr": 1,
        "plnOrdrSymbolSet": [
          {
            "plnOrdrSymbolPK": { "plnOrdrId": 1780000000000, "plnOrdrSymbolId": "<graphic id>",
                                 "plnOrdrOverlayId": "<uuid>" },
            "isDelete": "N", "isShared": "N", "creatorId": 10900, "updateSeqnr": 1,
            "drawEss": "<JSON string>"      // a STRING, not an object
          }
        ]
      }
    ]
  }
}
```

Points to note:

- `drawEss` is a JSON string embedded in JSON (double-encoded). Parse it with `JSON.parse` before inspecting it.
- `creatorId` is the constant `10900` in every generated record (default argument of `Plan.createOverlay` / `Plan.createSymbol`).
- `dttm` is `yyyyMMddHHmmss000 ` in UTC, with a trailing space.
- The loader reads only `poObj.plnOrdrOverlay[].plnOrdrSymbolSet[]` (`isDelete`, `plnOrdrSymbolPK.plnOrdrSymbolId`, `drawEss`). All other header fields are written for legacy consumers and ignored on load.

### 3.2 drawEss by geometry type

`SYM_GEO_TYPE` selects the builder. The save path handles these values; anything else falls back to shape inference (control points present means Area/Line style, `GEOM` or a point geometry means Point or UEI/FPoint depending on whether the SIDC is longer than 10 characters or `UEI === '1'`).

| `SYM_GEO_TYPE` | Main keys written |
| --- | --- |
| `Area`, `Line` | `SYM_GEO_TYPE`, `SID`, `SYM_NAME`, `CTRL_PTS[]`, `AMPLIFIER`, optional `DRAW_TYPE`, `ECHELON`, `FACE_GAP`, `ISFHAND`, `FRHNDSZ`, `FRHNDWDTH`, `drawExtendType`, `HEAD_RATIO`, `TAIL_FACTOR`, `SIDC`, `labelOptions`, `opacity`, and when a base line exists `BASE_LN_PTS{startPt,midPt,endPt}`, `BK_LN_DIST_RATIO`, `BK_LN_ANGL_RATIO`, `FRNT_LN_ANGL_RATIO` |
| `Point` | `SYM_GEO_TYPE`, `SID`, `SYM_NAME`, optional `SIZE`, `ANGLE`, `GEOM`, `AMPLIFIER`, `ISFHAND`, `SIDC`, `labelOptions`, `FRHNDSZ`, `FRHNDWDTH`, `opacity` |
| `FPoint` (unit / equipment) | `SYM_GEO_TYPE`, `SID`, `SYM_NAME`, `OPTIONS{...}`, `GEOM`, `AMPLIFIER: {}`, `UEI: '1'`, `SIDC`, `labelOptions`, `opacity` |

Point objects are `{ "type": "point", "x": <lon>, "y": <lat>, "sp": "WGS1SP" }`.

`AMPLIFIER` for Area, Line and Point always carries nine legacy fields: `UNIQUE_DESIG` (default `' '`), `UNIQUE_DESIG_ID`, `HIGHER_FORM`, `hfid`, `STAFF_COM`, `ADDL_INFO`, `MULTI_LINE_LABEL_TEXT`, `MULTI_LINE_LABEL_COLOR` (`'#000000'`), `MULTI_LINE_LABEL_ALIGN` (`'center'`), plus `DTG`, `DTGTO` and `TARGET_DESIGNATOR` when set. The SIDC is not inside `AMPLIFIER`; it is at the top level of `drawEss` (`SIDC`). For `FPoint` the amplifier text lives in `OPTIONS` (`uniqueDesignation`, `higherFormation`, `staffComments`, `additionalInformation`, and so on).

### 3.3 Normalization (Plan.ts)

`Plan.normalizeDrawEssForLegacyExport(raw)` and `Plan.normalizeDrawEssForRuntime(raw)` are public statics. They keep values that exist and fill legacy-safe defaults where a key is missing. They exist so files remain loadable by the legacy consumer that reads the same format.

Save (legacy export):

- Removes `extraSettings`.
- `Area`: `HEAD_RATIO` and `TAIL_FACTOR` become strings.
- `Point`: `labelOptions.textSize` and `labelOptions.haloColorSize` become strings; ensures `ISFHAND`, `FRHNDSZ`, `FRHNDWDTH` (default `0`) and `OFFSET` (default `'0'`).
- `Line`: ensures `DRAW_TYPE` (1), `drawExtendType` (1), `ISFHAND`, `FRHNDSZ`, `FRHNDWDTH`.
- `FPoint`: ensures `OPTIONS.SYM_NAME`, `roa`, `msn`, `hfid`, `ph`, `uniqueDesignationID`, `direction`, `quantity`, `reinforcedReduced` (all `''`), `ANGLE` 0, `ECHELON` `''`, `alphaNum` 100, `opacity` 1, `symType` `'FPoint'`; `OPTIONS.size` becomes a string; `labelOptions` becomes `{}`.
- Non-`FPoint`: `labelOptions` is merged over a default (`haloColor [255,0,0]`, `haloColorSize 5`, `color [0,255,0]`, `textSize 20`, `bold 1`, `italic 0`, `uLine 0`, `oLine 0`, `tLine 0`).

Load (runtime):

- Fills `FLAP_ANGLE` 45, `BK_LN_DIST_RATIO` 5, `BK_LN_ANGL_RATIO` 5, `FRNT_LN_ANGL_RATIO` 0.8, `FRNT_LN_DIST_RATIO` 1.5, `FLAP_DIST_RATIO` 3, and `extraSettings` `{ lineWidth: 3, size: 20, textSize: 12, opacity: 1 }`.
- Coerces stringified numbers back to numbers for `Area` (`DRAW_TYPE`, `FACE_GAP` default 5, `drawExtendType`, `HEAD_RATIO`, `TAIL_FACTOR`), `Point` (`SIZE`, `ANGLE`, `ISFHAND`, `FRHNDSZ`, `FRHNDWDTH`) and `FPoint` (`OPTIONS.size`, `alphaNum`, `ANGLE`, `opacity`).
- Copies `AMPLIFIER.TARGET_DESIGNATOR` to `drawEss.TARGET_DESIGNATOR` for `Point`.
- For `FPoint`, derives missing `OPTIONS.uniqueDesignation`, `higherFormation`, `staffComments`, `additionalInformation`, `dtg`, `location` from `AMPLIFIER`.

Hosts that generate plan files themselves (for example from a database) can import `Plan` from `MS/Engines/ImportExport/Plan` (`Plan.min.js` in the build) and use `new Plan()`, `Plan.createOverlay()`, `Plan.createSymbol()`, `plan.addOverlay()` and `plan.toJSON()`. `Plan.createSymbol(planId, overlayId, symbolId, drawEss, creatorId = 10900)` accepts `drawEss` as a string or object and normalizes it.

## 4. PAMS8 symbol JSON

### exportLayerToJSON(): object[]

Returns one `pams8-symbol` object per graphic across `TACT`, `TACT_PT`, `FORCE` and the legacy `milSymbols` layer. Returns `[]` (and logs an error) if the engine is not started. Graphics that fail to serialize are skipped silently.

### importLayerFromJSON(data: object[]): void

Calls the load callback (`SymbolEngine.loadSymbolFromJSON`) once per array item and logs a count. It does not validate the array, and it does not clear existing graphics. Loading the same file twice creates duplicates, or fails to load if ids collide (see the collab note in [14](14-faq-troubleshooting.md)).

### saveToFile(filename?: string): void

Downloads `exportLayerToJSON()` as `pams8_symbols_<Date.now()>.json`.

### loadFromFile(): void

Opens a file picker (`.json`, `.geojson`) and dispatches on content:

| Parsed content | Action |
| --- | --- |
| `type === 'FeatureCollection'` | `importFromGeoJSON` |
| `type === 'pams8-template'` | Template callback (error logged if none is registered) |
| JSON array | `importLayerFromJSON` |
| Anything else | Treated as one `pams8-symbol` object |

A Plan file is not accepted here; use `loadPlanFromFile()`. `loadFromGeoJSONFile()` is an alias of `loadFromFile()`.

### saveSymbolToJSON(graphic: Graphic): object

Serializes one graphic (available on `serializationEngine` only):

```jsonc
{
  "pams8Version": "2.0",
  "type": "pams8-symbol",
  "layerId": "ForceSymbolsLayer",       // origin layer id, else the symbol layer id, else FORCE
  "id": "<attributes.id>",
  "sidc": "10031000001101000000",        // amplifier.SIDC or drawEssentials.SIDC
  "amplifier": { /* copy of drawEssentials.AMPLIFIER, {} if none */ },
  "drawEssentials": {
    /* copy of attributes.drawEssentials without SCOPE and AMPLIFIER;
       CTRL_PTS, BASE_LN_PTS, GEOM rewritten as { x, y, spatialReference } */
  },
  "pinned": true, "xPct": 0.25, "yPct": 0.1   // only when screen-pinned
}
```

Coordinates in `drawEssentials` are written in the graphic's own spatial reference (typically Web Mercator, wkid 102100), with the spatial reference embedded. They are not converted to WGS84, unlike Plan and GeoJSON geometry. For a point with no `GEOM`, the geometry is taken from `graphic.geometry`.

### loadSymbolFromJSON(data: any): Graphic | null

`SymbolEngine` method that rebuilds one symbol. If `drawEssentials` contains `CTRL_PTS` (or legacy `_CTRL_PTS`), `BASE_LN_PTS` or `GEOM`, the symbol is re-created through `initialize(drawEssentials, amplifier, true)`, the same pipeline as interactive drawing, with the saved `id` as the graphic id. If the symbol class does not produce a graphic synchronously, the method builds the graphic directly (fallback). If there is no drawing data, it falls back to a legacy path that reads `data.geometry`/`geometryType` and `data.symbol`/`symbolType`. Returns the graphic, or `null` on failure (error logged to the console).

Recognised input keys: `id`, `sidc`, `amplifier`, `drawEssentials`, `layerId`, `graphicType`, `pinned`, `xPct`, `yPct`, `suppressDrawingLifecycle`.

## 5. GeoJSON

### exportToGeoJSON(): object

Returns a `FeatureCollection` of every graphic on `TACT`, `TACT_PT`, `FORCE` and `milSymbols`. Returns an empty collection (and logs an error) if the engine is not started.

Per feature:

| Part | Value |
| --- | --- |
| `geometry` | Point becomes `Point`, polyline becomes `MultiLineString` (`paths`), polygon becomes `Polygon` (`rings`). Web Mercator (102100/3857) is converted to WGS84. Other geometry types are omitted. |
| `properties.pams8` | `true` (import marker) |
| `properties.id` | `graphic.attributes.id` |
| `properties.layerId` | Layer the graphic was on |
| `properties.sidc` | SIDC |
| `properties.amplifier` | Amplifier object |
| `properties.drawEssentials` | Same shape as in `saveSymbolToJSON` (own spatial reference, not WGS84) |

Pinned (screen-anchored) graphics are excluded, since they carry a screen position rather than real geography. Graphics whose geometry is not a point, polyline or polygon are also skipped. Geometry in a spatial reference other than 102100/3857 is written as-is (not reprojected); treat that case as unverified.

### importFromGeoJSON(geojson: any): void

Restores symbols from a `FeatureCollection`. Non-collections are rejected with an error log.

- Only features with a truthy `properties.pams8` are imported. Features from other sources are counted and skipped; if nothing at all was imported and some were skipped, an error log states that they are not PAMS8 GeoJSON. There is no generic "GeoJSON to symbol" mapping for foreign data.
- The `geometry` is used only when `properties.drawEssentials` has none of `GEOM`, `CTRL_PTS`, `BASE_LN_PTS`. Then `Point` becomes `GEOM`; `LineString`, `MultiLineString` (paths flattened), `Polygon` (first ring) and `MultiPolygon` (first ring of first polygon) become `CTRL_PTS`, all tagged `spatialReference: { wkid: 4326 }`.
- Each feature is then loaded as a `pams8-symbol` (`pams8Version: '2.0'`).
- A feature that throws is counted and reported; the rest continue.

```ts
// Round trip through a host database
const fc = symbolEngine.exportToGeoJSON();
await fetch('/api/plans/12', { method: 'PUT', body: JSON.stringify(fc) });
// later
const saved = await (await fetch('/api/plans/12')).json();
symbolEngine.importFromGeoJSON(saved);
```

## 6. PowerPoint export

### exportPptxDeck(options?: PptxExportOptions): Promise<PptxExportResult | undefined>

Exported from `PptxExportCommands.ts` and also set as `window.exportPptxDeck` when that module loads (it is a side-effect import of `SymbolEngine.ts`). It lazy-loads `PptxExporter` and calls `PptxExporter.getInstance().exportDeck(options)`.

Requirements and behavior:

- `features.exportTools` must be `true` at call time, otherwise the promise rejects with `Export Tools disabled - enable features.exportTools in Settings`. It also rejects with `No active view to export` if no view resolves (the view comes from `window.symbolEngine.view` unless `PptxExporter.getInstance().start(getView)` was called).
- If `window.briefingEngine` has slides, the deck has one slide per briefing slide. With no briefing slides, it exports one slide of the current view.
- The first call injects the `pptxgen.bundle.js` script tag (section 6.2).
- Returns `undefined` for the default `output: 'download'`, and a `PptxExportResult` for the other outputs.
- Editable mode from a 3D view first asks the user whether to switch to 2D (exact) or continue (approximate) or cancel. If the user cancels, the promise resolves to `undefined` and nothing is exported.

Each option below falls back to the matching `exportTools.*` setting when omitted (see [08](08-settings.md)), then to the default shown.

| Option | Type | Default | Meaning |
| --- | --- | --- | --- |
| mode | `'flat' \| 'editable'` | `exportTools.mode`, else `'flat'` | `flat`: one screenshot per slide. `editable`: simple lines, areas and text become native PowerPoint shapes over a basemap raster (exact in 2D, approximate in 3D). MIL-STD picture markers and decorated tactical graphics stay in the raster. |
| format | `'png' \| 'jpeg'` | `exportTools.format`, else `'png'` | Screenshot format |
| explodeBuilds | `boolean` | `exportTools.explodeBuilds`, else `false` | One extra slide per staged-reveal build step |
| includeNotes | `boolean` | `exportTools.includeNotes`, else `true` | Attach slide notes as speaker notes |
| fileName | `string` | `pams8_briefing_<Date.now()>.pptx` | Output name |
| layout | `'16x9' \| '16x10' \| '4x3' \| 'wide' \| 'custom'` | `exportTools.layout`, else `'16x9'` | Slide size. Presets in inches: 16x9 = 10 x 5.625, 16x10 = 10 x 6.25, 4x3 = 10 x 7.5, wide = 13.3 x 7.5. `custom` uses `exportTools.deckWidth` x `deckHeight` in pixels at 96 DPI, clamped to 1 to 56 inches per side |
| compress | `boolean` | `exportTools.compress`, else `false` | Zip-deflate the package |
| slideNumbers | `boolean` | `exportTools.slideNumbers`, else `false` | Stamp slide numbers |
| useMaster | `boolean` | `exportTools.useMaster`, else `false` | Build on a generated slide master: classification banners, header and footer strips, title placeholder |
| meta | `PptxDeckMeta` | from `exportTools` | `{ title?, author?, company?, subject?, revision? }` document properties. Defaults: title `exportTools.deckTitle` or `'PAMS8 Briefing'`; the others from `exportTools.author`, `company`, `subject`, `revision` |
| output | `'download' \| 'blob' \| 'base64' \| 'arraybuffer'` | `'download'` | What to do with the finished package |

`PptxExportResult` (returned for non-download outputs):

| Field | Type | Meaning |
| --- | --- | --- |
| fileName | `string` | Resolved file name |
| slides | `number` | Slides written (build frames counted individually) |
| bytes | `number` | Package size in bytes |
| blob | `Blob` | Present when `output === 'blob'` |
| base64 | `string` | Present when `output === 'base64'`; no `data:` prefix |
| arrayBuffer | `ArrayBuffer` | Present when `output === 'arraybuffer'` |

```ts
// Send the deck to a service instead of downloading it
const res = await window.exportPptxDeck({ output: 'base64', layout: 'wide', useMaster: true,
  meta: { title: 'OPORD 12 brief', author: 'S3 Cell' } });
await fetch('/api/decks', { method: 'POST', headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: res!.fileName, data: res!.base64 }) });
```

Deck chrome (classification banner, header, footer, slide numbers, number format, skip-first) comes from the briefing's own deck chrome (`BriefingEngine.getChrome()`), with `exportTools.*` as the fallback per field. Header and footer text supports the tokens `{DTG}`, `{DATE}`, `{TITLE}`, `{SLIDE}`, `{SECTION}`, `{PAGE}`, `{PAGES}`, `{COMPANY}`, `{AUTHOR}`, `{SUBJECT}`. Font, theme-colour and right-to-left settings (`headFont`, `bodyFont`, `useSchemeColors`, `rtl`) are read only from `exportTools`, not from options.

Other export behavior confirmed in source:

- Slide sections (`Slide.section`) become PowerPoint sections. Overlay links (slide jumps and external URLs) are written as real hyperlinks. Relative jumps `lastViewed` and `endShow` cannot be exported and are dropped with a log line.
- Review comments are injected as native legacy PowerPoint comments, plus a private typed-comment sidecar (`https://ms-briefing.internal/typed-comments/v1`) so kind and metadata round trip through the importer (`PptxComments.ts`).
- Table auto-paging (`autoPage`) is disabled for a deck that contains overlay links, because paging inserts slides and would repoint the links. A log line says so.
- Chart overlays are emitted as native PowerPoint charts.
- A single slide is limited to 250 native shapes and 250 points per path in 2D (600 in 3D) in editable mode.

### 6.2 Loading pptxgenjs (window.PptxGenJS)

PptxGenJS is not an npm dependency of the library. It ships as an offline browser bundle, `MS/ThirdParty/PptxGenJS/pptxgen.bundle.js` (version 4.0.1), and is injected as a `<script>` tag on first use by the exported function `loadPptxGenJS(): Promise<any>` in `PptxExporter.ts`.

Behavior of `loadPptxGenJS()`:

- Returns `window.PptxGenJS` immediately if it already exists.
- Otherwise appends `<script src="MS/ThirdParty/PptxGenJS/pptxgen.bundle.js" async>` to `document.head`. The `src` is a relative URL, so the browser resolves it against the host page URL, not against the library module.
- Resolves with the constructor; rejects if the script fails to load or `window.PptxGenJS` is undefined afterwards. A load failure clears the cached promise, so a later call retries.
- The bundle also sets `window.JSZip`, which the importer reuses.

Host requirements:

1. Serve `dist/MS/ThirdParty/PptxGenJS/pptxgen.bundle.js` so that it is reachable at `MS/ThirdParty/PptxGenJS/pptxgen.bundle.js` relative to the page that hosts the map. `npm run build` copies `MS/ThirdParty` into `dist/MS/ThirdParty` (`copy-thirdparty`); copy that folder to the same relative location on the host.
2. Alternatively, load the bundle yourself before the first export (`<script src="...">`); `loadPptxGenJS()` then finds `window.PptxGenJS` and skips injection.
3. A host page that lives at a deeper path than the folder that contains `MS/` needs the file under that page's path, or a redirect or rewrite rule. The path is not configurable through settings.

## 7. PowerPoint import

Import is performed by `BriefingEngine.importPptxFromFile()` (see [12](12-briefing-collab-stylus.md)), which needs `features.briefing` enabled. It opens a file picker for `.pptx`, lazy-loads `PptxImporter`, parses the deck, and appends the slides to the current briefing.

### parsePptx(data: ArrayBuffer, opts: PptxImportOptions): Promise<PptxImportResult>

Exported (named and default) from `PptxImporter.ts`. It is a pure parser: it does not touch the briefing itself, so a host can call it directly and then place `result.slides` where it likes. PptxGenJS cannot read decks, so this is a purpose-built OOXML reader over `window.JSZip` (it calls `loadPptxGenJS()` first to obtain JSZip).

| Name | Type | Default | Meaning |
| --- | --- | --- | --- |
| data | `ArrayBuffer` | required | The .pptx bytes |
| opts.capturedIn | `'2d' \| '3d'` | required | Stored as `slide.view.capturedIn` |
| opts.defaultTransitionMs | `number` | `1000` | Stored as each imported slide's `transitionMs`. `BriefingEngine.importPptxFromFile()` passes `briefing.defaultTransitionMs` |

`PptxImportResult`: `{ slides: Slide[]; warnings: string[] }`. `warnings` is a list of human-readable notes about anything flattened or skipped (unreadable slides, dropped links, comment import failures, and so on).

Mapping, from the file's own header comment:

| PowerPoint | Briefing |
| --- | --- |
| Title placeholder | `slide.title` |
| Text boxes | `text` overlays |
| Preset rectangles, ellipses and other preset shapes | matching overlay kinds |
| Connectors | `line` / `arrow` overlays |
| Freeform shapes | `freehand` overlays |
| Tables (with merges) | `table` overlays |
| Charts | `chart` overlays (series from the chart part's cached values) |
| Pictures | Composited into one raster stored as `backgroundDataUrl` |
| Notes | `slide.notes` |
| Sections | `slide.section` |
| Hyperlinks | `overlay.link` (slide jumps, relative jumps, external URLs; URLs are scheme-checked) |
| Hidden slides | `slide.hidden` |
| Comments | `slide.comments` (typed metadata restored when the exporter's sidecar is present) |

Limits: at most 150 slides are read (`Deck has N slides - only the first 150 were imported` is added to `warnings`), and at most 250 overlays per slide. The parse and rasterisation run in the browser and can take a while on large decks.

Imported slides are screen-only: `view` has no `extent` or `camera`, so playback leaves the map untouched and the stored `backgroundDataUrl` is the slide. They can later be turned into map slides with `BriefingEngine.captureIntoSlide()`.

## 8. Versioning and compatibility

| Artifact | Marker | Rule |
| --- | --- | --- |
| Plan file | none | Identified structurally (`poObj.plnOrdrOverlay` array). Field compatibility is handled by `Plan.normalizeDrawEssForRuntime`, which fills missing keys and coerces types, so older and legacy-system files load. |
| PAMS8 symbol JSON | `pams8Version: '2.0'` | Written on every item. The loader does not check it. It accepts both current keys (`CTRL_PTS`, `BASE_LN_PTS`) and the older underscore keys (`_CTRL_PTS`, `_BASE_LN_PTS`), and a legacy geometry/symbol form. |
| GeoJSON | `properties.pams8: true` | Only the marker is checked. |
| Briefing document | `version: 12` on export | Import accepts versions 1 to 12; later fields are optional so older documents load unchanged. `importBriefing` does not check the number, only that `slides` is an array. Newer-than-12 documents are not handled by design. |
| Collab wire protocol | `PROTOCOL_VERSION = 2` | Peers on another version ignore each other; see [12](12-briefing-collab-stylus.md). |

The library itself has no migration layer beyond the tolerances above. Treat a plan or briefing written by a newer build as possibly unreadable by an older one.

## 9. Host recipes

Save and restore the whole picture with your own storage:

```ts
// SAVE
const graphics = symbolEngine.exportLayerToJSON();                 // or exportToGeoJSON()
const briefing = symbolEngine.briefingEngine?.exportBriefing();    // null if briefing is off
await store.put(planId, { graphics, briefing });

// LOAD (graphics first; slides refer to graphic ids)
const doc = await store.get(planId);
symbolEngine.importLayerFromJSON(doc.graphics);
symbolEngine.briefingEngine?.importBriefing(doc.briefing);
```

Notes:

- The Plan format has no data-only export (no method returns a plan object). `savePlanToFile` always downloads. To store plans in a database, use `exportLayerToJSON()` or `exportToGeoJSON()`, or build a plan object with the `Plan` class as described in section 3.3.
- `symbolEngine.briefingEngine` is `null` until the lazy load finishes. Listen for the `briefingEngineReady` event, which `SymbolEngine` dispatches on the view container and which bubbles to `document` (`detail.engine`).
- Ids: `attributes.id` survives a save and load, and briefings depend on it. `loadPlanSymbolsFromData()` rewrites ids on purpose, so briefing builds that target those graphics will not resolve for a placed formation.
- `features.saveLoad` only controls the right-click "Save / Load" submenu (Save All Symbols, Load Symbols, Save Plan, Load Plan, Export as GeoJSON, Import GeoJSON). The API methods work regardless of that flag.
- The harness (`src/main.ts`, `index.html`) wires the info-bar buttons `savePlanButton` and `loadPlanButton` to `serializationEngine.savePlanToFile()` and `loadPlanFromFile()`, and the API Test panel to `exportLayerToJSON`, `importLayerFromJSON`, `saveToGeoJSONFile`, `loadFromGeoJSONFile` and `window.exportPptxDeck()`.
