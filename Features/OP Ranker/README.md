Open in a browser, click 3–6 positions on hilly terrain, hit Run Analysis. Here is the complete explanation.

The core mathematical problem this solves
Placing OPs is a classic set cover / maximum coverage problem. You have N candidate positions and need the best K of them. The naive question is "which OP sees the most?" — but that is the wrong question. The right question is "which K OPs together see the most, with minimum overlap between them?" These have different answers. The highest-viewshed OP often occupies a dominant hilltop that sees the same ground as three others. The actually useful OP is the one that sees the dead ground behind the ridge the first one cannot.
Unique coverage contribution — the ranking metric
Every OP gets two numbers. Total viewshed — how much of the AO it can observe. Unique coverage — how much of the AO only it can observe, that would go blind if it were removed. Ranking is done on unique coverage, not total viewshed. This is the coverCount array: after building one boolean raster per OP, a cell is uniquely covered by OP_k when coverCount[i] === 1 AND raster_k[i] === 1. The percentage shown on each card badge is uniqueSeen / aoTotal. An OP with 35% total viewshed but 2% unique coverage is redundant — remove it and almost nothing changes. An OP with 18% total viewshed but 15% unique coverage is irreplaceable.
The horizon cache cuts computation by 99%
Each viewshed raster needs to know, for every grid cell, whether the cell is visible from the OP. Naively that means a full ray-cast per cell. Instead: pre-compute the maximum slope (horizon angle) along 180 bearings at 2° resolution. One ray per bearing, walked from the OP outward once. Then for each of the ~25,000 grid cells, look up the horizon for that cell's bearing (a single array access) and compare the cell's slope angle to it. The entire raster computes from 180 pre-walked rays rather than 25,000 individual ray-casts. Each additional OP only costs those 180 rays plus the grid loop — not another full set of ray-casts.
Greedy optimal set selection — the selectOptimalSet function
Picking the best K OPs out of N is NP-hard in general (you'd need to evaluate all C(N,K) subsets). For N=8, K=3 that's 56 combinations — tractable to brute-force. But the greedy algorithm is implemented here because it generalises and has a theoretical guarantee: it achieves at least (1 − 1/e) ≈ 63% of the optimal solution due to the submodularity of coverage functions. The logic is: start with an empty set. Each iteration, pick the OP that adds the most new AO cells to the existing selected set (marginal gain). Repeat K times. The ★ marker on a card and the green left border mean that OP is in the recommended set. The "Recommended set" strip at the bottom of the right panel gives the plain-language conclusion: "Use OP 2, OP 4, OP 6."
The gap zones are the actual deliverable
The red cells on the heatmap are the AO area not seen by any OP. This is the ground an enemy can mass in, move through, or emplace weapon systems without being observed. The gap area in km² is shown in the summary strip. A commander who sees that 34% of the AO is unobserved knows immediately that either the OP plan needs an additional position, or that uncovered ground needs to be controlled by fire rather than observation. The heatmap colour coding is: dark red = gap (0 OPs), blue = single coverage, cyan = two OPs, green = three or more (redundant — the most expendable coverage). The count heatmap lets a planner see immediately where they are over-investing in observation and where they have blind spots.
The overlap toggle draws the regions where multiple OP viewsheds intersect. This is useful for two reasons: cross-cueing (two OPs that both see the same ground can corroborate each other's reports) and redundancy identification (if three OPs all see the same valley, one of them can be repositioned to cover a gap without losing observation of that valley).
